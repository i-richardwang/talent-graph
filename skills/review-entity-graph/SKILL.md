复核 talent-graph 里 **company 实体图的结构质量**,把错位收口。这是 `/attribute-raw-name` 逐条建实体的事后兜底——单条创建没有全局视野,日积月累会沉淀出四类结构错位:

- **裂脑重复**:同一家公司被建成两个实体——下游分别命中、member 数被稀释
- **散落孤儿**:子公司没挂到它母体上——断了父子链,母体的 `subtree` 标签圈不到它的员工
- **用工法人壳**:只是母公司的法人 / 用工主体,却被单立成一个实体——制造"这个壳有 N 人"的假象
- **合资归错**:合资公司挂到了错误的归属方

下游名单标签靠 `员工任职 → entity → 父子链(subtree)→ tag` 派生命中,实体位置错了,标签就**漏人或混人**——这是修这些错位的唯一理由,也是判断一处改动值不值得做的标尺。

**现有的实体位置默认是对的。** 工作是校验、只修确有把握的错位,不是凭名字重排一棵"更整齐的树"再覆盖。吃不准就不动:挂宽(留在更上层母体)损失小,改错损失大。直连库查现状、做判决、用 CLI 写回。

## 判决依据:回到 raw + 员工岗位,不信 canonical / description

实体的 `canonical_name` 和 `description` 是上游建实体时写的,可能把一条 raw 查成了同名的**另一家**——只拿这两个字段互相比对来 review 是循环论证。真身锚在**这个实体名下的 raw_name,以及这些 raw 背后真实员工的岗位**(`employee_work_experiences.position_title`)。同名消歧吃不准时再深一层查员工简历正文(`employee_resumes.work_list`,每段含公司描述 + 岗位职责)——这是最硬的 ground truth。用 `bun --env-file=.env.local` + `pg` 直连查:

```js
const NORM = `btrim(regexp_replace(w.company_name,'[​‌‍﻿]','','g'),E' \t\n\r 　')`;
// 一个实体名下 raw 命中的去重员工数 + 岗位分布(判身份/归属的 ground truth)
await q(`SELECT w.position_title, count(DISTINCT w.emp_id) n
  FROM entity_aliases a
  JOIN employee_work_experiences w ON ${NORM} = a.raw_name
  WHERE a.entity_id = $1 AND a.entity_type='company'
  GROUP BY 1 ORDER BY 2 DESC`, [entityId]);
```

`company_name` 必须按 `src/db/normalize.ts` 的 `normalizeName`(剥零宽字符 + trim 含 NBSP / 全角空格)等价归一后再 JOIN——`entity_aliases.raw_name` 入库时归过,默认 `TRIM()` 只剥 ASCII 空白会静默漏命中。

岗位画像和实体声称的业务对不上(canonical 说是旅行搜索、人却全是通用平台岗),就是身份或归属存疑的信号。业务归属随时间变(并购 / 改名 / 拆分 / 出售),拿不准就 WebSearch 核实——核的是**现在还属不属于**,不是"当年被谁收购"(desc 记的收购方可能后来又把它卖了)。

## 候选从哪来:扫全库捞信号,人逐个判

没有现成脚本——按错位类型对全量 company 实体跑只读扫描,捞**候选**。捞出来的是 triage 候选、不是结论:**所有扫法都高召回、低精度**,每条都得回到上面的 raw + 员工岗位逐个核。各类错位的信号:

- **裂脑重复**:剥法人后缀(集团 / 股份 / 控股 / 有限公司…)取核心名分组、同核心名 >1 个实体 = 精度最高的信号;子串包含、`name_embedding` 向量近邻精度低(同业 / 番号 / 地区近义淹没),只配补充。
- **散落孤儿**:两条扫法互补,各抓一类。① 剥法人后缀取某集团品牌词作 hub,找 canonical 带该词、却不在该 hub 子树里的实体——抓名字带母体品牌的孤儿。② 扫 root 实体 description 里的被动归属语(被 X 收购 / 控股、成为 X 全资子公司、并入 X),解析出归属方再在库里匹配——抓**被收购方名字跟母体毫不相干**的孤儿(EMC↔Dell、客如云↔阿里,名字类扫法天生扫不到)。两条都得逐条回核当前控制权:desc 是上游写的、只作信号。
- **用工壳**:靠岗位查——子实体名下员工岗位画像与母体无从区分、且无独立品牌 / 业务线特征,就是壳;不靠名字扫。

## 错位与修法(都只接 UUID,破坏性操作前先 `--dry-run` 核对)

**和另一个实体其实是同一家** → `entity merge` 收敛成一个。survivor 选**知名简称**那个(HR / 员工会用来指认这家雇主的最熟知名字),不是股票简称、不是法人全称。merge 不继承 loser 的 parent——若 loser 挂着母体而 survivor 没有,合并后要把 survivor 挂回那个母体。

**只是母公司的用工 / 法人壳** → `entity merge` 并回母体。判据是它**有没有独立存在的理由**:有辨识度的雇主品牌、或可独立分析的业务线(行业归类与母体不同)→ 留(即使员工不多);品牌已消亡 / 从来不是品牌、没有可独立分析的业务、员工岗位画像与母公司无从区分 → 壳,并回。**壳判据看品牌 / 业务线,不看员工多少。**

**标准名用错了**(用了股票简称 / 法人全称而非知名简称)→ `entity rename`;**description 写错了身份**(把别家身份写成自己)→ `entity set-description`。

**是另一家的一部分,但自身有辨识度** → `entity set-parent` 挂到母体下(默认 `subtree`,母体标签覆盖它)。`parent_id` 只服务下游一件事:给母体打"雇主系"名单标签时,沿父子链把员工圈进来。所以一处挂载对不对,只回答一个问题:**给母体打这个雇主系标签,这家的员工该不该算母体这一系的人。**

答案不取决于谁控股、占多少股,而取决于**谁在实际经营这门生意、这家的员工在谁的体系里干活**。一家公司可以被某个资本方控股,却根本不算它"这门生意的一部分"——顺控股链一路上追,每家最后都挂到 PE、指数基金、控股平台这种只做财务持有的方,圈出来的"系"就没有分析意义了(先锋领航持有几乎所有上市公司,没人会把这些公司的员工都算成"先锋领航系")。

- **母体在经营它、员工算母体这一系 → 挂**:母体自建 / 孵化的业务臂(京东物流、新浪微博——哪怕后来独立上市、品牌很响);收购后已并进母体、品牌也溶掉的(Dell EMC、展讯并进紫光展锐);母体把它当自家业务线实际经营的合资 / 收购(广汽经营广汽菲克 / 广汽本田、腾讯音乐收喜马拉雅、陌陌收探探)。**合资里母体占一半、甚至不控股都不影响——只要这门生意是它在经营,员工就是它这一系。**
- **没人拿它当自家生意经营、只是被持有 → 独立**:母体只是被动财务投资人、或已出售剥离不再经营;控制方是把它当投资组合资产的纯财务方 / 无关多元集团(钢铁炭素集团靠破产重整接盘一家航司——它不经营航空,航司员工不算它这一系)。**控股方只是财务持有时,绕过它、挂到真正经营这门生意的体系**(麦当劳中国被一家 PE 控股,但整个就是麦当劳在华业务——挂麦当劳,不挂那家 PE)。

**独立上市、独立品牌、自主运营、体量反超、合资各占一半**,都不是判据:既不能把一个母体在实际经营的业务推成独立(京东物流仍属京东、广汽菲克仍属广汽),也不能把一个没人经营、只被财务方持有的独立公司硬挂上去。**只看谁在经营这门生意,不看持股数字。**

`parent_id` 编码的是这种**持久归属**(谁经营、控制权这类稳定事实),不是易变的内部组织架构 / 事业群——大集团常年重组,追架构是没尽头的维护、对圈人也无收益;中间层只保留稳定的品牌 / 业务节点,已解散的行政中间层拆掉、子实体直接上挂稳定母体。

## 反复出现的陷阱:同名不一定同一家

名字相同、缩写相同、description 看着像,**都不等于**同一家或有从属关系——这是污染最大的来源。判合并 / 挂父子前,得有 raw + 员工岗位 + WebSearch 真正对得上的证据;只凭名字像就连,会把不同员工群混进一个实体。改名时间线是好用的证伪器(某员工在职年份早于这家改成现名的年份,这条 raw 就不是它)。已经**拆分独立、被出售剥离**的(母公司已不再控股),也不该再挂回去。
